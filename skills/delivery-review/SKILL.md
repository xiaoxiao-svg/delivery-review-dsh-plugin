# 交付协作工作流（Loop 模式，DeepSeek Harness 移植版）

> "你不知道远比你知道的要重要的得多。"——塔勒布

**执行入口：`/delivery-review` 命令。** 本文件是方法论与数据模型参考。命令内部已用 `.delivery-review/state.json` 状态机驱动循环，不依赖模型记忆轮次。

---

## 元认知原则

### 边界感知三层

| 层级 | 含义 | 必须输出 |
|------|------|---------|
| 已知 | 确定检查过，结论明确 | ✅ 确认 / ❌ 有问题 |
| 不确定 | 检查了但没把握 | ⚠️ + 原因 |
| 未检查 | 根本没覆盖到的维度 | 🔍 列出（最重要） |

**每个交付节点必须输出「未知清单」——列出 AI 无法确认的风险点。这个清单比检查清单更重要。**

### 审查结论三通道（第 4 层输出）

| 通道 | 含义 | 去向 |
|------|------|------|
| risk | 确定（或高置信）的问题，带证据等级 | 触发修复 |
| 存疑清单 | 看了但拿不准的点（含经验猜测） | 不触发修复，人工验收判断 |
| 未知清单 | 没看 / 无法确认的维度 | 人工验收补查 |

## 角色与隔离

| 角色 | 执行者 | 权限 | 职责 |
|------|--------|------|------|
| 修复工程师 | `subagent_fixer` 子代理 | 读写代码 | 改代码、自检、处理 risk |
| 资深审查者 | `subagent_reviewer` 子代理 | **零命令权限（工具层 toolFilter allow 白名单：仅 read/read_image/glob/grep）** | 两段式独立审查（第一性原理本质审查 → 症状审查）、报 risk（带证据等级 + 与目标的关系）、对抗自查、打分、确认收敛 |
| 方案审查者 | `subagent_planner` 子代理（按需触发） | **零命令权限（工具层强制）** | 方案输出后、用户确认前，从产品视角审查方案（四项检查），结论只呈现用户，不进状态机 |
| 编排者 | 主 Agent / `/delivery-review` | 读写 + spawn | 确认上下文、输出方案与目标、驱动 loop、解析子代理结论、裁决、人工验收、生成交付报告 |

> 审查者的「零命令」由 `subagent_reviewer` 工具实例的 toolFilter allow 白名单在工具层强制（只保留只读工具），不靠 prompt 请求。它看不到 diff 的问题由插件自动生成审查材料解决（见下），因此不需要任何命令权限。

## 通信机制与数据模型（DSH 原生子代理消息通道，本版与 Claude 版的核心差异）

### 通信：不再使用 git notes

- 子代理（fixer / reviewer / planner）的**最终回复文本就是结论通道**：fixer 输出 review/done/dispute；reviewer 输出 risk/score/approve/confirm/withdraw；planner 输出四项检查结论
- 编排者从返回文本解析结论并驱动状态机，**不需要代写任何留言**（Claude 版因审查者禁 Bash 需编排者代写 git notes）
- 轮次间上下文由编排者在下一轮 spawn 的 prompt 中显式携带（目标、材料路径、risk 列表、dispute 内容、轮次号）
- risk 标识：`R<轮次>-<序号>`（如 R1-2），state.json 的 `last_round_risk_ids` 存这些标识

### 存储

- 审查材料（自动生成）：`<仓库根>/.delivery-review/review_material.md`——插件监听 `tools/post-execute`（write/edit/pwsh/bash 后）自动刷新，编排者每轮审查前可用 `refresh_review_material` 工具兜底。含改动清单 / 完整 diff（>800 行截断）/ 新建文件清单（untracked）。审查者 Read 该文件获取改动全貌，用 Read/Grep 核实代码
- 循环状态（机器判定）：`<仓库根>/.delivery-review/state.json`
- 角色指令：`delivery_review_role` 工具按需取回（fixer / reviewer / planner）
- 路径落位：`.delivery-review/` 与交付报告 `docs/` 固定在仓库根目录（按 `git rev-parse --show-toplevel` 定位），不在子目录创建
  ```json
  {
    "round": 0,
    "consecutive_clean": 0,
    "last_score": 0,
    "exit_reason": "",
    "max_rounds": 3,
    "file_mod_counts": {},
    "last_round_risk_ids": []
  }
  ```

| 字段 | 类型 | 用途 |
|------|------|------|
| `round` | int | 当前轮次 |
| `consecutive_clean` | int | 连续无新增 risk 轮数（用于 converged 判定） |
| `last_score` | int | 上一轮质量分（用于 quality_gate 判定） |
| `exit_reason` | string | 退出原因（空 = 继续） |
| `max_rounds` | int | 最大轮次上限 |
| `file_mod_counts` | object | 各文件被修改次数（用于 oscillation 检测，任一文件 ≥ 3 次即触发） |
| `last_round_risk_ids` | string[] | 上一轮 risk 标识列表（`R<轮次>-<序号>`，用于判定新增 risk） |

### 结论类型（子代理最终回复中的结构化结论）

| type | 谁发 | 含义 |
|------|------|------|
| `review` | 修复方 | 改动说明 + 意图声明 + 自检 + 未知清单 |
| `done` | 修复方 | 对某条 risk 的处理结果（引用 R<N>-<K>） |
| `dispute` | 修复方 | 对某条 risk 的反驳（附理由与证据，引用 R<N>-<K>） |
| `risk` | 审查方 | 问题描述 + 标识 + 分级 + 证据等级 + 与目标的关系（必填） |
| `score` | 审查方 | 本轮质量评分 + 收敛判断 |
| `approve` | 审查方 | 所有 risk 已解决，建议人工验收 |
| `confirm` | 审查方 | 收到 dispute 后自我核查结果（仍坚持 → 退出 loop，人工裁决） |
| `withdraw` | 审查方 | 撤回原 risk（误判） |

### 两段式审查（第一性原理，delivery-reviewer 强制）

1. **本质审查（先做）**：目标还原 → 核心断言提取 → 断言验证（带证据等级）→ 本质差距（目标 vs 改动 gap）
2. **症状审查**：bug / 边界 / 回归 / 测试 / 超范围重构 / 偏离目标（原六项）
3. **对抗自查（每轮必做）**：对每条正式 risk 三问——反证（修了目标真会达成吗）/ 根因（是因还是果）/ 目标本身（是否可验证）；P0/P1 额外给「fixer 可能的反驳 + 为何仍坚持」
4. **「与目标的关系」填不出** = 非本质问题，降 P2 或进存疑清单

### 证据等级（risk 必带字段）

| 等级 | 含义 | 处理规则 |
|------|------|---------|
| 已验证 | 实际运行/测试观察到的 | 正式 risk |
| 可复现 | 给出了复现步骤（未实际运行） | 正式 risk |
| 代码推断 | 读代码推断的（无运行依据） | 正式 risk，但**不允许报 P0** |
| 经验猜测 | 无具体依据的怀疑 | **不算 risk**，只能进存疑清单 |

> P0（最严重）必须带"已验证 / 可复现"证据；状态机统计 risk 数与 P0/P1 判定时，**排除经验猜测级**（它不进入 risk 流）。

### 风险分级

| 级别 | 含义 | 处理要求 |
|------|------|---------|
| P0-阻塞 | 安全漏洞、数据丢失、功能不可用 | 必须修复才能退出 loop（需已验证/可复现证据） |
| P1-重要 | 逻辑错误、性能退化、边界缺失 | 必须修复或说明不修复理由 |
| P2-建议 | 代码风格、命名、可维护性 | 可 defer，人工验收时酌情处理 |

## Loop 退出条件（由 state.json 状态机判定，优先级从高到低）

1. **oscillation / dispute 未解** → 强制退出，移交人工裁决
2. **converged**：连续两轮 `risk==0` 或 `新增 risk==0` → 理想退出
3. **quality_gate**：`质量分 >= 7` 且无 P0/P1 → 次优退出
4. **max_rounds**：达到 `max_rounds`（默认 3）→ 兜底退出

> risk 数 / 新增 risk / P0/P1 判定均只统计**正式 risk**（证据等级为已验证/可复现/代码推断），存疑清单不参与统计。新增 risk 指与上一轮 risk 标识集合相比新提出的（正文不重复）。
>
> **状态机执行纪律**：oscillation 检测依赖 `file_mod_counts` 字段（任一文件修改 ≥ 3 次即触发），新增 risk 检测依赖 `last_round_risk_ids` 字段（当前轮 risk 标识列表减去上轮列表）。这两个字段在 state.json 中持久化，不依赖 LLM 记忆或心算。编排者每轮必须输出完整的 state update block，包含这两个字段的更新。

## Dispute 机制

```
审查方发 risk（R<N>-<K>）
  ↓
修复方不同意 → dispute（反驳理由 + 证据）
  ↓
编排者将反驳转达审查方 → 审查方自我核查
  ├─ 仍认为有问题 → confirm → 退出 loop，人工裁决
  └─ 发现误判   → withdraw → 继续 loop
```

> 经验猜测级问题不算 risk，不存在 dispute 流程；存疑清单在人工验收时统一判断。

## 用户介入（任意时刻）

- **检查点**：每轮子代理返回后、状态机更新前，编排者检查用户是否有新消息，有则先输出进度摘要再对齐
- **打断**：用户中断子代理，编排者恢复后优先处理用户消息
- **目标变更** = 与 Step 2 相同的完整重置（state.json 归零 + 删旧材料 + 记录新目标）；**仅澄清** = 轮次延续
- 响应最迟不迟于当前子代理返回

> fixer 被打断可能留下半成品：重新对齐后以**当前工作区状态**为起点，不基于旧目标续写。

## 人工验收（最后一道防线：裁决权不可由 AI 代理）

红线拆两层：
- **裁决权**（通过/不通过）不可由 AI 代理——必须用户行使
- **验证执行**（跑测试 / 查日志 / 收集证据）可由用户声明交由 AI 代验，输出标注证据等级（已验证 / 代码推断），最终裁决仍由用户拍板

| 范围 | 内容 | 必须/可选 |
|------|------|----------|
| 改动点 | 修复方修改过的代码对应功能 | 必须 |
| 未解决项 | loop 中未解决的 risk | 必须 |
| 审查方存疑清单 | 拿不准的点（含经验猜测） | 必须 |
| 双方未知清单 | 修复方与审查方都无法确认的风险 | 必须 |
| 震荡点 | 反复修改的部分 | 必须 |
| 回归测试 | 原有功能是否被破坏 | 可选 |
| 体验检查 | 操作顺畅度、提示清晰度 | 可选 |

## 交付报告

Loop 结束后（无论验收结果），编排者把**本轮**子代理最终回复与状态机结论整理为交付报告写入运行项目 `docs/delivery-review-<日期>-<HHmm>.md`：目标 / 方案（含用户选择）/ 轮次摘要 / 已解决与未解决 risk / 存疑清单 / 未知清单 / 验收结论（未通过则标注原因与待办）/ AI 代验结果（如有）。报告是否提交 git 由用户决定。

## 附：塔勒布元认知速查

1. **我知道什么？** —— 确定检查过的
2. **我不确定什么？** —— 检查了但没把握的
3. **我不知道什么？** —— 根本没想到要检查的（最重要）
4. **如果我错了，后果是什么？** —— 下行风险不对称性
5. **这个改动重复一万次，会在某一次崩溃吗？** —— 遍历性检验

> 火鸡在被杀前的每一天都通过了「自检清单」。未知清单才是真正的防线。
